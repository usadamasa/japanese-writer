# 設計文書の骨格 — 図・ナビゲーション・意思決定の軸

複数の設計判断と構造を扱う長めの文書に重ねて適用する規範｡Phase 1.4 (重点先行) と Phase 1.5 (見出し草案) の「文章の骨格」に対して、本 references は「図とナビゲーションと意思決定の軸」という視覚・構造の骨格を扱う｡

適用するかどうかは文書の内容で判定する｡設計判断が 1 個以下で、構造を図で示す必要もないなら適用しない｡

scope 節 (対象 / 対象外) の書き方は Phase 1.3 に従う (本 references では扱わない)｡

## 1. 中心概念図を冒頭に置く

詳細セクションに入る前に、文書が扱う中心概念を 1 枚の図で示す｡読者が全体像を持ってから細部に入れるようにする｡

- **冒頭に置く**: 背景・課題の直後、個別の設計判断より前に「そもそも何をしようとしているか」の概念図を置く｡文章だけで中心概念を説明しない｡
- **周辺要素を削ぎ落とす**: 図には核心の関係だけを残す｡登場要素が多いと中心が埋もれる｡本筋に関係しない上流・下流・付随コンポーネントは落とす｡
    - 悪い例: 中心が「イベント到着 → 振り分け → 処理の実行」なのに、入力ストレージ・設定・出力層・ユーザー操作まで全部描く｡
    - 良い例: 「イベント到着 → 振り分け → 処理の実行」の関係だけに絞る｡
- **多重度・不特定多数を図で表現する**: 実態が「1 対 1」でなく「1 対 多」「不特定多数」なら、それが伝わるように描く｡代表ノード 1 個で済ませない｡
    - 悪い例: 実際は多数が並ぶ処理単位を 1 個のノードで描く｡
    - 良い例: 「利用者ごとに不特定多数が定義される」と subgraph で複数ノードを描く｡

## 2. 択一の設計判断は各案を対等な構成図で並置する

択一の設計判断は、各案を **同じ粒度の構成図** で並べる｡文章だけで比較しない｡

- 各案の構成図を並置したうえで、直後に判断軸の比較表を置く｡
- 図の粒度・スタイル (ノードの種類、色分け) を案の間で揃える｡片方だけ詳細だと公平な比較に見えない｡

### 2.1 決定表の条件セルは 4 状態を区別する

条件と結論を並べた表 (決定表) では、条件セルを空欄にして済ませない｡空欄は「その問いに条件として存在しない」のか「条件だが結論に効かない」のかを落とす｡独自記号を発明せず、確立した語彙 (don't care) に寄せて次の 4 状態を見た目で区別する｡

| 表記 | 意味 |
|---|---|
| **太字の値** | その行の結論を決める条件 |
| 細字の値 | その行が適用される前提条件 |
| `DC` (薄いグレー・斜体) | その問いの条件ではあるが、この行の結論には影響しない |
| `N/A` (薄いグレー・斜体) | その問いにはそもそも条件として存在しない |

凡例は表の下部に置き、各記号の意味を具体的な行番号で例示する (「No.5 の条件は No.7-8 の前提になる」のように指す)｡スプレッドシートでも Markdown の表でも同じ規則を使う｡

## 3. TOC を冒頭に挿入する

長い構造化文書は、冒頭 (H1 見出しの直後) に目次を置く｡読者が全体構成を把握し、目的の節へ直接飛べるようにする｡

- Python-Markdown 系の静的サイトジェネレータ: `[TOC]` マーカー (toc 拡張が有効な前提)｡
- wiki: 目次マクロ｡
- 短文には不要｡

## 4. 中心の意思決定を軸に構造化する

最大の設計判断を独立したセクションとして立て、それに従属する判断をぶら下げる｡見出しの front-load (最重要を h2、従属を h3、結論を h3 に埋めない) 自体は Phase 1.5 が扱う｡本節が足すのは **従属関係の明示** である｡

- 「最大の意思決定は X である」と明示し、他の判断 (権限・コスト・デプロイ等) が X に依存することを本文で述べる (「〜はこの選択に依存する」)｡
- 従属する設計要素は「X に依らず必要な要素」と「X に依存する要素」のように、軸との関係でグルーピングする｡

## 5. 未決事項と根拠の扱い

断定の可否そのものは Phase 2.3 (論証の厳密さ) と Phase 2.16 (読者への誠実さ) が扱う｡本節が足すのは、exploring 段階の設計文書に固有の書き方である｡

- **未決は方針・論点として書く**: Phase 2.3 の「根拠で確定していない命題を断定に変えない」を、設計文書では「〜する方針」「〜を目指す」「論点として残す」の定型で書く｡
- **要検証を明示する**: 議論参加者の主張で裏取りが済んでいないものは「要検証」と明記し、確定前に行う検証を書き添える (Phase 2.16「確認していないことを確認したかのように書かない」の設計文書向けの具体化)｡
- **括弧書きで別概念を並置しない**: 「A (B)」は B が A の言い換えか下位か上位かが曖昧になり混乱する｡両者の関係は本文で述べる (Phase 2.15 の同格挿入 = 同一の指示対象を指す丸括弧とは別で、別概念の並置を戒める)｡
    - 悪い例: 状態の持ち主を「実行側か、定義 (基盤) 側か」と書く (定義も実行も基盤の要素なので、括弧の並置が両者を対立概念に見せてしまう)｡
    - 良い例: 「実行側も定義側もどちらも基盤の要素であり、どちらが状態を持つかは排他ではない」と本文で関係を述べる｡
