# 日本語技術文書の文章規範 (japanese-tech-writing)

<!-- writing-gate-disable pink-elephant -->

> このファイル自身は規範を「説明・例示」する性質上、 規範違反パターン (e.g./i.e./etc./あなた/`**...**:` リスト形式・区切り線「─」 説明・表セル末尾の句点なし等) を本文に大量に含む｡
> よって prh と一部の ai-writing/technical-writing ルールを ファイル全体で disable している｡
> 却下案の痕跡も例示として持つため、 writing-gate の pink-elephant も同様に disable している｡
> 実際の文書 (wiki/ADR/Design Doc 等) では disable せず、 全ルールを適用する｡

日本語で技術的な原稿 (書籍の章・記事・解説文・ADR・Design Doc など) を書く・推敲するときは、以下の規範に従う｡発火タイミングは三段:

- **Phase 1 (構成検討)**: これから書き始める前に｡読み手・文書の種類・scope・重点先行・見出し草案・書かないことを決める｡
- **Phase 2 (執筆)**: ドラフトを書きながら｡整形・段落・論証・視点と語り・一文の長さ・能動態・数字日付・箇条書き・略号・リンクテキスト等を意識する｡
- **Phase 3 (推敲・self-check)**: 書き上げ直後に｡軽量なチェックリストで論理構造・読者視点を確認する｡最後に [[proofread]] を呼ぶ｡

個人の声・投稿文の指紋 (Slack/times などのカジュアル投稿) は本スキルの外にある書き手ごとの文体スキルが担当する｡本スキルは「論証と段落の規範」を扱う｡同じ文書でも、表記の指紋は文体スキル、論証の構造は本スキル、と併用する｡併用時の優先度は Phase 1.2 の文書の種類別マトリクスで決める｡文体スキルは [[proofread]] の `style_check` で差し込む｡差し込みが無ければ、文書の種類別マトリクスの「個人文体」列は無視して fofr 強化規範だけを適用する｡

# Phase 1: 構成検討 (書き始める前に)

ドラフトを書き始める前に、次の項目を決める｡決定事項は心の中で持っておくか、必要なら scratch メモに書き出す｡Phase 1 の成果物は「見出し草案 + scope 節」｡

## 1.1 読み手と目的の特定

- **誰が読むか** を具体化する｡「チームのエンジニア」ではなく「この API サーバーを運用する Backend エンジニア (TypeScript 経験あり、Rust 未経験)」のように｡
- **読み終わった後に何を判断・実行できるべきか** を一文で書ける状態にする｡「読者がこの ADR を読み終えたあと、Rust 採用の是非を 5 分で判断できる」のように｡
- **読み手の既知 / 未知** を区別する｡既知の概念は説明を省く、未知の概念は短い導入を入れる｡
- 典拠: 文化庁「公用文作成の考え方」§1, fofr "Start from user need"

## 1.2 文書の種類 (medium) の判定

文書の種類を判定する｡文書の種類は適用すべき規範の組み合わせを決める｡文書の種類の判定が決まらないと、個人文体と fofr 強化規範のどちらを優先するかが決まらない｡

| 文書の種類 | 個人文体 | fofr 強化規範 | 衝突時の優先 | scope 節 |
|----|----|----|----|----|
| Slack / times | ◎ | × | 文体 | 不要 |
| Flow 文書 (議論メモ・週次・探索) | ○ | △ | 文体 | 任意 |
| Stock 文書 (運用手順・FAQ) | △ | ○ | fofr | 必須 |
| ADR | × | ◎ | fofr | 必須 (Decision / Out of scope) |
| Design Doc | × | ◎ | fofr | 必須 (Goals / Non-Goals) |
| blog / 長文記事 | ○ | ○ | 文脈で判断 | 推奨 (冒頭 1〜2 文) |
| 議事録 | ○ | △ | 文体 | 任意 (アジェンダで代替) |
| 書籍の章 | × | ◎ | fofr (k16shikano 原典) | 必須 (この章で扱うこと / 扱わないこと) |

**マトリクスの読み方**:

- ◎ = 強適用、○ = 中庸、△ = 弱適用、× = 適用しない
- 「個人文体」は書き手ごとの文体スキル (推量・自虐・句読点などの指紋) を指す｡差し込まれていなければこの列は無視する
- 「衝突時の優先」が `fofr` の文書では、個人文体の指紋 (推量・自虐) を抑える
- 「衝突時の優先」が `文体` の文書では、fofr の強い断定や能動態徹底をゆるめてよい
- 「衝突時の優先」が `文脈で判断` の文書 (blog) では、本人の声で書く blog なら文体、技術解説の長文なら fofr｡Phase 1 の時点で明示する

**認知リズム規範の適用**:

書籍の章・blog 長文・長文ノート (>3000 字目安) では、`references/cognitive-rhythm.md` を Phase 2 執筆前に読む｡ADR/Design Doc/Stock 文書 では同 references の「開幕の緊張」と「状況 vs 文書テスト」のみ弱適用する｡Slack/Flow/議事録では適用しない｡強度の詳細は同 references の「文書の種類別強度の調整」節を参照｡

**設計文書の骨格規範の適用**:

ADR / Design Doc / Stock 文書 (複数の設計判断・構造・図を扱う文書) では、`references/design-doc-scaffolding.md` を Phase 2 執筆前に読む｡中心概念図の冒頭配置・択一案の構成図並置・TOC 挿入・意思決定の軸での構造化・未決事項の書き方 (方針/論点/要検証)・括弧書きでの別概念並置の回避を扱う｡Slack/Flow/議事録では適用しない｡

## 1.3 主題と scope の宣言 — 書いてあること / 書いてないこと

1 文書 1 主題｡含めること (Goals) と含めないこと (Non-Goals / Out of scope) を author の頭の中で決め、文書の種類によっては文書冒頭に**節として書き出す**｡

**author が頭で決める**:

- この文書で主張する命題は何か
- 主張を支える例・データ・根拠は何か
- 議論しない論点 (= 別文書に逃がす論点) は何か

**文書本体に scope 節を書き出す** (文書の種類ごとの必須/任意は 1.2 のマトリクス参照):

| 文書の種類 | 節名のテンプレ |
|----|----|
| ADR | `Decision` / `Alternatives considered` / `Out of scope` |
| Design Doc | `Goals` / `Non-Goals` |
| 書籍の章 | 章冒頭リード「この章で扱うこと / 扱わないこと」 |
| Stock 文書 | 冒頭リード「対象 / 対象外」 |
| blog / 長文記事 | 冒頭 1〜2 文で「この記事で扱うこと」を宣言 (節立て不要) |
| Flow 文書 / 議事録 | 議論が散らかりそうなら冒頭に書く｡通常省略可 |
| Slack | 不要 |

**狙い**: 読み手が冒頭を読むだけで要不要を判断できる｡「Y について書かれていない」という不満を先回りで処理する｡

## 1.4 重点先行 (倒立ピラミッド)

結論 → 詳細 → 背景 の順で書く｡文書全体・各節・各段落・各文の **すべての階層** で適用する｡

- 文書冒頭の段落: 結論 (この文書が主張すること) を最初に書く｡背景は後ろに｡
- 節冒頭: その節の主旨を最初に書く｡導出は後ろに｡
- 段落冒頭: 段落の topic sentence を最初に書く｡詳細は後ろに｡
- 文の先頭: 文の主語 (=何の話か) を早く出す｡修飾語の積み重ねで主語を遠ざけない｡

**異常系は正常系の後ろへ回す｡** 入力がどう弾かれるか、失敗したら何が出るか、制約に触れたときどうなるかは、手順の本文に混ぜず付録か末尾の節に置く｡読み手が手順を追っている間、それは読まなくてよい情報である｡付録の冒頭に「正しく渡しているなら読まなくてよい｡断られたときだけ見る」と前置きを書いて、いつ戻ってくるかを示す｡

典拠: 木下是雄『理科系の作文技術』(重点先行), fofr "Front-load everything, inverted pyramid"

## 1.5 構成案 (見出し草案) の作成と front-load 検証

ドラフトを書き始める前に、**見出しだけを上から並べた骨格** を作る｡見出しを順に読み上げて、文書の主旨と論理が伝わるか確認する｡

- 「はじめに」「背景」「まとめ」のような **情報のない見出し** を排除する｡見出しがその節で答える問い・扱う対象を指してるか確認する｡
- 見出しの **front-load**: 最も重要な見出しが上位 (h2) に来てるか｡背景や前提が h2 に来ていて結論が h3 に埋もれてないか｡
- 見出しの **過剰な装飾を避ける**: 「種別──主題」のような区切り線詰め込みをしない｡単一の自然な句にする｡
- 見出し草案ができたら、Phase 2 の執筆はこの骨格を埋める作業になる｡

見出しの細則は `references/phase2-norms.md` の 2.14「見出しの付け方」を参照｡

典拠: fofr "Headings: front-load them, descriptive", k16shikano「見出しの付け方」

## 1.6 書かないことの決定

読み手の記憶と注意は有限資源｡書き始める前に、書かない方針を決めておくと、Phase 2 で詰め込み過ぎを防げる｡

- **読者が自力で補える前提** は書かない｡「TypeScript の型システム」のような既知事項を冒頭で解説しない｡
- **後で参照する必要のない固有名** (一回しか出ないファイル名・関数名・識別子) は出さない｡「仕様書」「金額計算のユーティリティ」のような一般的な言い方で済ます｡
- **装飾的精度** (時刻・HTTP ステータス・カバレッジ率など、議論に効かない数字) は最初から落とす｡
- **章冒頭の関係ない詳細** を入れない｡これから例で扱う内容に関係しない情報を詰め込まない｡

執筆中の負荷管理の細則は `references/phase2-norms.md` の 2.15「読み手の負荷の管理」を参照｡

典拠: k16shikano「読み手の負荷の管理」, fofr "Cut everything that does not add meaning"

# Phase 2: 執筆 (ドラフトを書きながら)

Phase 1 の構成案 (見出し草案 + scope 節) を埋めていく｡

**執筆を始める前に `references/phase2-norms.md` を Read する｡** 執筆中の規範の本体はそちらにある｡

# Phase 3: 推敲・self-check (書き上げ直後に)

書き上げ直後に、人間 (=書き手) が頭で点検する **軽量チェックリスト** ｡機械で拾える項目 (太字・半角句読点・一文の長さ・受動態・LLM 表現) は次の [[proofread]] に任せる｡self-check は **論理構造と読者視点** に絞る｡

## 3.1 self-check 項目

項目 7 ([[proofread]]) が最終ゲートなので、項目 8〜10 は項目 7 より前に済ませる｡

1. **重点先行ができてるか** (構造)
   - 文書冒頭・各節冒頭・各段落冒頭で「最も重要な点」が最初に来てるか｡
   - 背景・前置きで始まる節がないか｡

2. **scope 節で要不要が一目で分かるか** (読者の期待値)
   - Phase 1 で決めた「書いてあること / 書いてないこと」が冒頭に明示されてるか｡
   - 文書の種類別マトリクスで必須の文書 (ADR/Design Doc/書籍の章/Stock 文書) は省略してないか｡

3. **読者の前提知識を超えてないか** (読者の理解可能性)
   - Phase 1.1 で特定した読み手が、未知の概念につまずかないか｡
   - 専門用語や略語に必要な短い導入が入ってるか｡
   - 逆に、既知の概念を冗長に説明してないか｡

4. **段落先頭文だけで論証が追えるか** (パラグラフライティング)
   - 各段落の 1 文目だけ拾い読みして、主旨と論理の流れが追えるか｡
   - topic sentence が「結論」を述べてるか (詳細・例証から始まってないか)｡

5. **論証が一方向に進んでるか** (論理の流れ)
   - 結論 → 反論 → 結論 で往復してないか｡
   - 譲歩 (「ただし」「とはいえ」) で宙吊りになってないか｡
   - 前方参照した論点 (「次節で扱う」など) が後で本当に回収されてるか｡

6. **例が主張の範囲を支えてるか** (誇大主張の回避)
   - 挙げた例が実際に主張全体を支えてるか｡
   - 支えてないなら、主張の範囲を例に合わせて狭めたか｡

7. **proofread を呼んだか** (機械点検への引き渡し)
   - [[proofread]] を `medium` 指定で呼ぶ｡
   - wiki ページ → `medium: "wiki"`
   - docs 系リポジトリ → `medium: "docs"` (+ `config_root` にリポジトリ root を指定)
   - 探索メモ・長文ノート → `medium: "note"`
   - タスク本文・チケット説明などの短い下書き → `medium: "short-draft"`

8. **認知リズムが効いているか** (該当する文書のみ)
   - 判定した文書の種類が **書籍の章 / blog 長文 / 長文ノート** のときのみ実施｡
   - `references/cognitive-rhythm.md` の「10. 推敲手順」を回す:
     - **漏出テスト** — 「緊張」「回収」「認知モード」「着地」など本規範自身の術語を grep で検索し、本文に流出していないか確認｡
     - **緊張元帳** — 全ての問い・仮定・約束を列挙し、回収位置に印を付ける｡末尾にちょうど 1 個の未回収を残す｡
     - **ビート点検** — 3 個以上の長い断定が連続する箇所を探す｡
     - **境界点検** — 二人称呼びかけと読者への要請が章冒頭/末尾以外に混入していないか｡
   - ADR/Design Doc/Stock 文書 のときは「開幕の緊張」と「状況 vs 文書テスト」のみ確認｡
   - Slack/Flow/議事録のときはスキップ｡

9. **設計文書の骨格が整っているか** (該当する文書のみ)
   - Phase 1.2 の文書の種類が **ADR / Design Doc / Stock 文書** のときのみ実施｡
   - 中心概念図が冒頭にあり、周辺要素を削ぎ落として核心に絞れているか｡多重度 (1 対多・不特定多数) が図で表現されているか｡
   - 択一の設計判断は各案を対等な構成図で並置し、判断軸の表を添えているか｡
   - TOC を冒頭に挿入したか｡
   - 最大の意思決定を軸に、従属する判断がぶら下がる構造になっているか｡
   - 未決事項を断定していないか (「〜する方針」「論点として残す」「要検証」)｡括弧書きで別概念を並置していないか｡
   - 根拠: `references/design-doc-scaffolding.md`

10. **制作過程の痕跡と却下した案が残っていないか** (読者視点)
    - 対話を重ねて書いた文書で実施する｡議事録・対話ログは対象外｡
    - [[sanitize-artifacts]] を読み、同スキルの点検チェックリストを回す｡
    - 会話で受けた指示・修正フィードバック・意図伝達のために渡された例・回避した手段・制約そのものが本文に残っていないか｡
    - 制約は宣言ではなく、制約を満たした記述として現れているか｡
    - 方針転換の経緯注記 (「以前は X だったが現在は不要」) を本文に残していないか｡
    - 途中で捨てた案が、逐語・意味・理由・注意配分・視覚の 5 層のどこかに残っていないか｡
    - 落ちた箇所は語を差し替えて通そうとせず、その節を捨てて書き直す｡
    - 根拠: [[sanitize-artifacts]]

## 3.2 self-check と proofread の役割分担

| 観点 | self-check (本節) | proofread |
|------|----|----|
| 視点 | 書き手の主観 | subagent の客観 |
| コンテキスト | 主コンテキスト | 別コンテキスト (proofreader subagent) |
| 検出対象 | 論理構造・読者視点 (機械では拾えないもの) | 表記・LLM 表現・冗長・テンプレ違反 (機械点検 + rubric 判定) |
| タイミング | 書き上げ直後 | self-check 通過後の最終ゲート |
| 重み | 軽い (人間が暗算で回す) | 重い (subagent 別コンテキスト) |

両者は **重複が健全** ｡前者が気付きベース、後者が網羅ベース｡self-check が見落とした太字過多を proofread が拾い、proofread が判定しにくい「重点先行できてるか」を self-check が拾う｡

## 3.3 文書の種類別 self-check の強度調整

Phase 1.2 で判定した文書の種類によって、self-check 項目の強度を調整する｡

- **fofr 優先の文書** (ADR / Design Doc / Stock 文書): 項目 1〜6 を **厳しく** 適用｡特に項目 1 (重点先行) と項目 2 (scope 節) を必ず通す｡項目 8 (認知リズム) は「開幕の緊張」と「状況 vs 文書テスト」のみ弱適用｡
- **文体優先の文書** (Slack / Flow 文書 / 議事録): 項目 3 (読者の前提知識) と項目 4 (段落先頭文) を優先｡項目 5 (論証の一方向性) は短文ではゆるめてよい｡項目 8 (認知リズム) はスキップ｡
- **認知リズムを全面適用する文書** (書籍の章 / blog 長文 / 長文ノート >3000 字): 項目 1〜7 に加えて項目 8 の全手順 (漏出テスト・緊張元帳・ビート点検・境界点検) を回す｡
- **文脈で判断する文書** (blog 短文・中程度の記事): Phase 1 で決めた優先度に従う｡
- **制作過程の痕跡の点検は文書の種類によらず適用する**｡漏出は文書の格式ではなく制作の経緯で決まるため、Slack 投稿にも起こる｡例外は議事録・対話ログで、会話の記録そのものが成果物なのでスキップする｡

# 個人文体スキルとのすみ分け

個人文体スキルは書き手ごとに用意し、[[proofread]] の `style_check` で差し込む｡本スキルは文体スキルの中身を知らない｡

| 観点 | 個人文体スキル | 本スキル (japanese-tech-writing) |
|------|---------------------|----------------------------------------|
| 守備範囲 | 個人の声・投稿文の指紋 | 論証・段落の規範 |
| 主な対象 | Slack 投稿・times・短文 | 技術書の章・記事・ADR・Design Doc・調査メモ |
| 句読点 | 文体スキルが決める | 半角「｡ ､」(同梱の textlint config が強制する) |
| 推量・自虐 | 文体スキルが決める | 推量は不確実性が真に必要な箇所のみ｡自虐は使わない |
| 絵文字 | 文書の種類に応じて使う | 使わない |
| 適用範囲 | 全面 (文書の種類別に強度が変わる) | 全面 (Phase 1.2 の文書の種類別マトリクスで強度が決まる) |
| 衝突時 | 文体優先の文書 (Slack/Flow/議事録) では本スキルより優先 | fofr 優先の文書 (ADR/Design Doc/Stock/書籍の章) では文体スキルより優先 |

両者は排他ではない｡同じ wiki ページでも、全体の論証構造は本スキル、句読点や用件直行の指紋は文体スキル、と重ねて適用してよい｡Phase 1.2 の文書の種類別マトリクスで優先度を決める｡

# textlint で機械点検する

Phase 3 の self-check 項目 7 で必ず [[proofread]] を呼ぶ｡引数:

- `file_path` または `text`: 点検対象
- `medium`: wiki → `"wiki"`、docs 系 → `"docs"`、探索メモ・長文ノート → `"note"`、短い下書き → `"short-draft"`
- `config_root`: `.textlintrc.json` を置いてあるディレクトリ｡docs 系リポジトリならリポの root path｡省略すると [[textlint-check]] 同梱の config が効く
- `style_check`: 書き手の文体スキルがあれば `{"skill": "<skill 名>"}` で渡す｡Phase 1.2 の「個人文体」列はこの差し込みで初めて効く

textlint-check (機械点検) は proofread の内側で呼ばれるので、直接呼ぶ必要はない｡

検出される指摘の例:

- 太字強調・コロン継続・hype 表現・冗長表現 (Phase 2.12 の "preset で機械検出するもの" 節参照)
- 全角句読点の混入 (prh で半角「｡ ､」へ autofix する)
- 一文の長さ・連続助詞・二重否定 (`preset-ja-technical-writing`)
- 英文略号 (e.g., i.e., etc.) の混入 (Phase 2.9、textlint-check の prh ルールセット)
- 「あなた」の使用 (Phase 2.4、同 prh)
- 数字表記の全角混入 (Phase 2.7、同 prh)

autofix がその場で適用されるのは表記ゆれ (全角数字・半角句読点) だけ｡意味に関わる指摘は検出だけされて Tier 2/3 として呼び出し元に返る｡語を差し替えても文の骨格は元のまま残るので、その文をまるごと書き直す｡ユーザー確認や強制 push の判断はそこで行う｡

# 完了時のゲート

Phase 3 を回さずに書き終えても、セッションを閉じるときに同梱の Stop hook が最後の点検を当てる｡そのセッションで編集した `.md` を `writing-gate` が見て、次のどれかが残っていれば完了がブロックされる｡

- 同じ語尾の文が段落内で 3 文以上続いている
- である体とですます体が混ざっている
- 制作過程の痕跡・却下した案の痕跡が逐語で残っている

ブロックされたときは、指摘された語を別の語へ置き換えるのではなく、その語を含む文を書き直す｡ゲートが見るのは文書全体の性質と逐語の漏出だけなので、通ったことは Phase 3 を済ませたことにはならない｡外部へ出す文書なら [[proofread]] を続けて呼ぶ｡

会話の記録そのものが成果物である文書 (議事録・対話ログ) は既定で除外されている｡それ以外で外す必要が出たら [[writing-feedback]] の「文書の種類で切り替える」節に従う｡
